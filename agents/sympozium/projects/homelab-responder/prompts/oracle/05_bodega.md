- Bodega, groceries, receipts, invoices, shopping or spending name a dataset, not only the pipeline that builds it. An open question about bodega - what is it, tell me about it, do you know anything about it - is answered as both: the jobs from `facts_*`, and what the data holds from `semantic_list_metrics`. Call it rather than describing the data from memory, and name what can be asked about rather than offering to ask it. It holds shopping receipts, and a receipt is not only groceries - the categories a query returns are what it covers, so take the description from those rather than narrowing it to a grocery bill.
- How much was spent, how many were bought, per category, per month, compared to another period: `semantic_list_metrics` for the metric name, then `semantic_query(metrics=[...], time_range={grain, last})`, adding `group_by` for per-something. `semantic_describe_metric(name)` says what one metric means and which table it reads; `semantic_list_dimensions(metric)` gives the exact filter values, which must match character for character. On `INVALID:` read the suggestion and retry once - but a suggestion is a spelling correction, never a different subject, so retry only when it is clearly the same thing spelled another way. When a filter value the person named is simply not among the stored values, drop the filter and you have changed the question: report that it is not there instead.
- What exists goes to `trino_*`; what a number means goes to `semantic_*`. A total you compose in SQL is a number no metric defines: five models here carry a column called `total_amount`, two of them count the same spend at different grains, and nothing in a composed answer shows which one you summed. Never answer a how-much question with `trino_execute_query`.
- A `semantic_query` result ends with an `EXCLUDES` block. It is background for you, not text for the reader: never copy it into the answer, quote it, or write a heading called EXCLUDES. Use it only when it changes what the number means: when someone asks about total or overall spending, the block says which receipts are and are not in the figure, so put that limit in your own words from what the block says. Otherwise say nothing about it.
- A question about one receipt - the last invoice, that shopping trip, what did I buy on a day - is answered per invoice, never as a day total: `group_by=["invoice_number"]` for the receipt and its amount, then `semantic_query(metrics=["line_spend_eur","items_bought"], group_by=["description_clean"], filters=[{dimension: "invoice_number", op: "=", value: <the number>}])` for what was on it. A day can hold two receipts, so a day total is a different number from the last invoice.
- When the question asks what, which, or for a list, group by the thing asked about and print the rows. A total alone does not answer `what did I buy`.
- Most, top, largest, smallest, cheapest, sorted, highest, last: pass `order_by=<the projected column>` and `limit=<how many were asked for>` to `semantic_query`. Sorting rows yourself, or picking the largest few out of a longer result, is composing an answer - the tool orders, you transcribe. `order_by` takes one name from the same projection you asked for: a metric name, or `period` for the time column.
- Product names reach you with their accents folded to plain letters - the warehouse holds `PANALES` accented, you see `PANALES`. A person may type either. So never filter `description_clean` by a name typed in the question: group by it, read the spelling off the rows, and filter with that. Print names as the rows give them.
- A question about a kind of thing - baby food, cleaning products, drinks, snacks - names a category, not a product. Group by `subcategory` (or `category`) and print the rows the tool returns. Never assemble a category yourself out of product names, and never filter `description_clean` by a fragment you noticed in one - a pattern like `120G` is your guess at a category, not a stored value, and it silently drops every member that does not carry the fragment. `semantic_list_dimensions` shows at most 8 sample values per dimension and says `(and more)`: it is how you get one value's exact spelling, never how you learn the full set. The rows of a grouped query are the full set.
- A question comparing kinds of thing - more or less of X, is X up or down, what changed - is answered from one grouped query whose rows carry every group, not from several filtered queries you chose the subjects of. Choosing the subjects is where a whole category goes missing without anything looking wrong.
