# Design

## Context

See `proposal.md` for motivation and `specs/content-writer/spec.md` for the behavior contract. Only the constraints that shape the n8n approach are recorded here.

- `agents/n8n/workflows/linked_in_post_sharing.workflow.json` already implements this exact shape for LinkedIn: a `scheduleTrigger` + `manualTrigger` read `content_queue` in the `content_planner` sheet; `select_article_to_post` picks one `QUEUE` row; `update_status_in_progress` claims it; `download_content` fetches the source page; `execute_post_creator` calls the `LinkedIn Post Creator` sub-workflow; `notification_accept` is a Slack `sendAndWait` double approval; on reject, `notification_retry_or_cancel` is a `sendAndWait` `customForm` (Retry/Cancel + Feedback) and the creator re-runs with the feedback; then `execute_image_creator`, `convert_image`, `notification_sent_image`, `notification_accept_image`, `switch_user_accept_image`, and finally `send_2_linkedin_omImage` publishes and `update_status_published_a` records it.
- The workflow's `settings.errorWorkflow` is set, and `linked_in_post_sharing_error.workflow.json` is the companion that turns an error into a Slack notice and an `ERROR` status. `catch_errors.workflow.json` is the generic notifier.
- Prompt files live in this repository under `agents/n8n/prompts/` and are fetched at runtime by the `DownloadTemplate` workflow, which reads `agents/n8n` from the GitHub backup repo using `BACKUP_GITHUB_REPO_*` env vars and a GitHub credential; `LinkedIn Image Creator` fetches `prompts/linkedin_image_prompt.md` and `datasets/image_motifs.json` the same way.
- Images are generated by an HTTP Request to LiteLLM `POST http://datahub-local-core-data-litellm.data.svc.cluster.local:4000/openrouter/images` (model `google/gemini-3.1-flash-image`, `aspect_ratio`, `resolution`), and `convert_image` decodes the returned base64 into binary for Slack and publishing.
- Slack approvals use `n8n-nodes-base.slack` `sendAndWait`. In the existing flow the review channel is `#workflows` (`C08RQNXQV3P`).
- The blog repository (`github.com/alvsanand/alvsanand`) is MkDocs + Material with the **blog plugin** (`plugins: [blog, macros, glightbox]`; `archive: false`, `categories_toc: false`), with no `posts_directory` override, so the default `blog/posts/` under `docs_dir` applies.
- Post conventions, read off the repo: files at `docs/blog/posts/<YYYYMM>-<slug>.md`; front-matter `date: YYYY-MM-DD`, `authors: [alvsanand]` (from `docs/blog/.authors.yml`), `categories: [...]`; the H1 is the post title. The blog plugin derives the URL from the front-matter `date` and the title, not the filename — verified from `site/blog/2026/09/15/the-open-source-trojan-horse/`, so a post's URL is `https://alvsanand.com/blog/<YYYY>/<MM>/<DD>/<title-slug>/`.
- Image conventions, read off the repo: files under `docs/img/`, referenced from the post as `![alt](/img/<file>){ width="80%" }` (the `attr_list` extension supplies the width, `glightbox` supplies the lightbox). The image filename is independent of the post slug (e.g. `oss-trojan-horse.jpg`).
- `.github/workflows/pages.yml` runs `mkdocs gh-deploy` on push to `main`.

## Gate findings

Reconciled on 2026-10-15 against the studio that actually landed: the change was written before the studio was rewritten, and six of its assumptions no longer hold.

- **The studio has no `SPEC_JSON`.** `agents/n8n/workflows/visual_studio.workflow.json` declares no such input (0 occurrences). Its inputs are `CONTENT, ASSET_TYPES, FEEDBACK, FORCE, STYLE, SCENES, EXTRA_PROMPT, SESSION_ID` and its answer is `{RUN_ID, SESSION_ID, STATUS, ASSETS[]}`. A frozen spec cannot be passed back; a retry continues a session instead (D9).
- **`add-visual-studio` is archived** (`2026-10-01-add-visual-studio`), so the capability is read from `openspec/specs/visual-studio/spec.md` rather than from a pending change, and this change blocks on nothing.
- **The asset type ids were invented.** `hero_static` and `infographic_static` are not in `agents/n8n/datasets/visual_types.json`; the registry declares `image, animation, animation_linkedin, animation_linkedin_video, svg, deck`, with `default_types: [image]` and `max_types_per_request: 3`. A blank `ASSET_TYPES` now defaults to `image,svg` (D6).
- **An agent asset no longer carries its bytes.** The studio stores the render in Garage through the utils server and answers with `S3_KEY`/`S3_BYTES`; only the raster `image` type still carries a data URL, because those bytes are made inside n8n. The caller fetches by key — the shape `LinkedIn Post Sharing`'s video branch already uses (D6).
- **No run row exists for the studio to review from.** The row and `visual_studio_table` are gone, so `article_assets` is the only per-asset state, which is what D2 already assumed.
- **Data Tables are proven in this instance but not in its API.** Four live workflows carry `n8n-nodes-base.dataTable` nodes, so the node type works; whether the public REST API can create one stays [UNVERIFIED], so creation is a UI setup step (D2).
- **The gate ids this design carried (A3, A7, C1-C4, G26, G29-G35) were never defined anywhere**, having come from a review pass whose findings were not recorded. Each only restated the sentence it followed, so the tags are dropped and the reasons kept.

## Goals / Non-Goals

**Goals:**
- Clone the proven `linked_in_post_sharing` structure so the blog lane behaves exactly like the LinkedIn lane a reviewer already knows.
- Keep both review gates (article, image) and the retry-with-feedback loop, matching the existing Slack UX.
- Keep blog write access narrow: a token that can write `alvsanand/alvsanand` and nothing else.
- Keep the failure path wired, because an unwired n8n failure is invisible in logs, Slack and Prometheus at once.

**Non-Goals:**
- Changing `linked_in_post_sharing`, `linked_in_post_creator`, `linked_in_image_creator` or `content_queue`. The LinkedIn lane keeps working untouched.
- A new runtime, a Sympozium agent, an MCP server, or any cluster change.
- Producing the topic: rows are authored human-side in `article_queue`.
- Multi-author support, translations, or automatic cadence selection.

## Decisions

### D1. Build a new workflow family, cloned from the LinkedIn one

New entry-point workflow `Article Content Writer` plus an `Article Creator` sub-workflow and a companion `Article Content Writer Error`, all modeled node-for-node on the LinkedIn equivalents. Assets come from the `visual-studio` capability's Visual Studio workflow, invoked as a sub-workflow, so this change authors no image of its own. The sub-workflows differ where the artifact differs: long-form article prompts and a long-form length budget, and the publish step commits to GitHub instead of calling the LinkedIn node.

*Alternatives considered:* add a channel branch to `linked_in_post_sharing` — rejected: one workflow's failure would then break both the live LinkedIn lane and the blog, and the prompt/length differences would leak into the LinkedIn path. Parameterize `execute_post_creator` with a channel — rejected for the same coupling; the sub-workflows are cheap and the repo already keeps one per artifact shape.

### D2. `article_queue` mirrors `content_queue`, with persisted per-artifact state

New page in `content_planner` with statuses `QUEUE`, `IN_PROGRESS`, `WAITING_APPROVAL`, `PUBLISHED`, `CANCELLED`, `ERROR` as the existing flow uses them, plus the article's own review state (`ARTICLE_STATUS` `DRAFT`/`APPROVED`/`REJECTED`, `ARTICLE_ROUND`, `ARTICLE_FEEDBACK`, `ARTICLE_TITLE`). The existing LinkedIn flow keeps both approvals in run state; persisting them makes a died execution resumable and makes the "preserve the other approval" requirement observable.

Assets are **not** columns here: per-asset state (type, status, round, feedback, object key, committed path) lives in this change's own `article_assets` DataTable keyed by `ENTRY_ID` + `ASSET_TYPE`, and every asset (the hero included) is reviewed and retried from it. The singular `IMAGE_*` columns are dropped: two descriptions of one image is how they drift. The Visual Studio workflow itself keeps no per-article state — it is generic and stateless — so the review state can only live here.

The article draft is stored in an **n8n DataTable** (`article_drafts`) keyed by `ENTRY_ID`, not in a Sheets cell; the sheet keeps only `ARTICLE_REF` pointing at it. A DataTable has no 50,000-character cell limit, which removes the draft-size risk entirely. The table is **instance state, not a repo artifact**: its creation is a documented setup step, and a missing table is a loud error rather than an empty article. The `n8n-nodes-base.dataTable` node is already carried by four live workflows in this repository, so the mechanism is proven in this instance; whether the public REST API can create a table is [UNVERIFIED], so creation is a UI step.

Proposed `article_queue` columns: **input** `ENTRY_ID, TOPIC, DESCRIPTION, LINK, CATEGORIES, ASSET_TYPES, MAX_WORDS, EXTRA_PROMPT, PRIORITY, ORIGIN`; **row lifecycle** `STATUS`; **article review** `ARTICLE_STATUS, ARTICLE_ROUND, ARTICLE_FEEDBACK, ARTICLE_TITLE, ARTICLE_REF`; **outcome** `PUBLISHED_URL, COMMIT_REF, PUBLISHED_AT, EXECUTION_ID, ERROR, UPDATE_DATE`. `ASSET_TYPES` is a human-declared comma-separated list of ids from the studio's registry, defaulting to `image,svg` when blank; the `image` hero is always in the requested set, since the blog emits no `og:image` and the hero is what a social preview shows, and a declared list adds to it rather than replacing it. `CATEGORIES` is validated against `datasets/blog_categories.json`; `MAX_WORDS` defaults to 1200 when blank. Names mirror `content_queue` where an analogue exists (`STATUS`, `EXTRA_PROMPT`, `MAX_WORDS`, `PRIORITY`, `ORIGIN`, `PUBLISHED_AT`, `EXECUTION_ID`, `ERROR`, `UPDATE_DATE`). `ARTICLE_TITLE` is the model's H1 and the source of the plugin-derived URL slug; `row_number` is supplied by n8n and is not a column.

*Alternatives considered:* reuse `content_queue` — rejected: different columns, different status semantics, and a single mistargeted update would corrupt the LinkedIn backlog. Single `STATUS` only, as LinkedIn — rejected because it cannot express "article approved, asset rejected" across a restart. Keeping `IMAGE_*` — rejected: a per-asset row already carries that state. A Sheets cell or a linked Drive doc for the draft — rejected in favour of the DataTable: no cell limit and no second document to link.

### D3. Prompts are files under `agents/n8n/prompts/`, fetched at runtime

New `article_writer_system.md`, `article_writer.md`, and `article_image_prompt.md`, fetched through the existing `DownloadTemplate` workflow exactly as the LinkedIn prompts are. They follow the repo's AI prompt policy: short, literal, action-oriented; inputs and required output shape; no copied schemas or current data. The article prompt takes topic, description, optional source content, optional feedback **and the requested `ASSET_TYPES`**, because it must emit one `<!-- asset:<type> -->` marker per requested type; the image prompt takes the article text.

*Alternatives considered:* inline prompts in the workflow JSON — rejected by the repo rule that prompts are files, never inlined. A new prompt store — rejected; the existing download path already works and has a build-time variable check.

### D4. Slack approvals reuse `sendAndWait`, exactly as the LinkedIn flow

Article approval is `sendAndWait` with `approvalType: double`; rejection opens the `customForm` with Retry/Cancel and a Feedback textarea; the retry re-enters `Article Creator` with `FEEDBACK`. Because Slack section text caps around 3000 characters and a long-form draft is several times that, the draft is reviewed as a **Slack file upload (or a short snippet plus a DataTable link)**, not inline message text; assets, which are small prompts and previews, stay inline. Each asset is sent as a Slack file, then approved separately with its own `sendAndWait` double. A resumed review posts into the **same thread with the round number**, so a reviewer acting on a superseded draft is visible rather than silent (G32/G34).

*Alternatives considered:* interactive Block Kit and a webhook — rejected; the existing `sendAndWait` flow already carries free-text feedback and is the pattern the reviewer uses. Sending the draft inline — rejected; it truncates at the Slack section limit. A form node — rejected; it would block on a web UI rather than Slack.

### D5. Publish with one commit through the GitHub Git Data API

The publish step is an HTTP Request with a bearer GitHub credential — the **existing n8n GitHub credential reused**, whose write scope is [UNVERIFIED] and must be confirmed on first publish — performing `GET ref` → create one blob per file (the article as utf-8, each approved asset as base64) → create tree → create commit → `PATCH ref`, so the article and every approved asset land in a single commit and a half-published set is impossible. Before the tree is built, `GET contents/docs/blog/posts` derives and disambiguates the title slug. Front-matter is composed deterministically in a Code node (`date`, `authors: [alvsanand]`, `categories`) rather than asked of the model. Each asset is written to `docs/img/<frozen-slug>-<type-id>.<ext>`, the extension being the format the studio's registry declares for that type, and referenced from the article at its `<!-- asset:<type> -->` marker, matching the existing posts, and `PUBLISHED_URL` is computed from the blog plugin's verified pattern (`https://alvsanand.com/blog/<YYYY>/<MM>/<DD>/<title-slug>/`) rather than guessed.

*Alternatives considered:* the n8n `github` node — its file resource does not express a single atomic multi-file commit and binary handling is awkward; the raw Git Data API is deterministic. Two commits — rejected: a failed second commit publishes an article without its assets. A PR instead of `main` — not chosen; the requirement is direct to `main` once all artifacts are approved, and a PR can be added later by changing this one step only. On a non-fast-forward `PATCH ref` because another commit landed on `main` in the window, the step re-fetches the ref and retries once and never force-pushes; a second failure surfaces as a commit error.

### D6. Assets come from the studio's registry, and the caller fetches their bytes

Assets are produced by the `visual-studio` capability's Visual Studio workflow, invoked as a sub-workflow. The set is the entry's `ASSET_TYPES` — the `image` hero always, plus whatever the row declares, `image,svg` when the row is blank — or the registry's own `default_types` when the call leaves `ASSET_TYPES` empty; the ids are the registry's, so adding a type is a `visual_types.json` edit and never a graph edit, and a request over `max_types_per_request` comes back SKIPPED with a reason rather than dropped. `FORCE`, `STYLE` and `SCENES` are left blank by this change, so the composer chooses its own form and scene count; there is no per-entry column for a pinned form yet.

Bytes arrive two different ways, because the raster type is authored *inside* n8n and the composer types are not. The `image` type returns its data URL inline with the answer — measured on the LinkedIn lane at ~2.3 MB in `execution_data` for one 1080x1350 png — while an agent-authored type is stored in Garage by the utils server and answers with `S3_KEY` and `S3_BYTES`. The entry point signs that key through the utils server's `temp_retrieve` and downloads the signed URL as a file, exactly as `LinkedIn Post Sharing` does for its video, and `article_assets` stores the key rather than the bytes. The raster's own bytes are the exception and are stored on the asset row (`DATA_BASE64`): they have no durable handle anywhere else, and without them a commit resumed after a died run has nothing to upload. The cost is bounded - measured 943,620 bytes for one 928x1152 hero - and no other type pays it.

The studio's run `STATUS` is `PARTIAL` whenever a requested type is unavailable and `FAILED` when every asset carries an error, so the caller branches on each asset's own `STATUS`/`ERROR` and never on the run status: an unresolvable type comes back as an asset carrying the reason, and one such asset must not take the rest of the set with it.

*Alternatives considered:* author the hero in this change with the `LinkedIn Image Creator` pattern — rejected; it duplicates the studio's raster branch and gives the blog a second image path to keep in step. Make the hero an agent type so nothing is carried inline — rejected; the registry's `image` type is what produces a photographic hero, and the studio already owns that branch. Generate assets before the article is approved — rejected; assets derive from the settled article, and approving the article first means the common path generates them once.

### D7. The entry point carries the error workflow; sub-workflows raise

`Article Content Writer` sets `settings.errorWorkflow` to `Article Content Writer Error`, which mirrors `linked_in_post_sharing_error`: on error it reads `article_queue`, selects the row for the failed execution, sets `STATUS=ERROR`, and notifies Slack. The sub-workflows return an `ERROR` field on failure (as `execute_post_creator` does) and the parent's `check_subworkflow_error` routes it to the same error handling, so no failure is swallowed.

*Alternatives considered:* reliance on the generic `catch_errors` workflow — rejected: it notifies but does not clear the `IN_PROGRESS` row, leaving it stuck.

### D8. Selection is deterministic and claims before working

`select_article_to_queue` picks the lowest `row_number` among `STATUS=QUEUE`; the next node sets `STATUS=IN_PROGRESS` before any LLM call, so a crash leaves a claimed row rather than a double-processed one. Topic rotation is dropped: blog cadence is low and correctness matters more than variety here.

*Alternatives considered:* copy the LinkedIn priority+rotation logic — rejected as unnecessary for a low-frequency lane and because `article_queue` has no `PRIORITY` column yet.

### D9. The article workflow owns every review gate and the single commit

`Article Content Writer` is the only owner of the Slack review gates and of the one commit. The Visual Studio workflow is generic and stateless: it is invoked as a sub-workflow with `(CONTENT, ASSET_TYPES, FEEDBACK, FORCE, STYLE, SCENES, EXTRA_PROMPT, SESSION_ID)`, returns one envelope of `{RUN_ID, SESSION_ID, STATUS, ASSETS[]}`, and performs no review and no commit itself.

Re-presenting a rejected asset means calling it again with that asset's type, the entry's session id and the feedback. The session is derived from the entry (`blog-<ENTRY_ID>`), and the adapter decides from the session directory whether that call authors or edits, so a retry continues the composition the rejection named instead of producing an unrelated one, while a session that was swept degrades to a first authoring rather than editing nothing. There is no frozen-spec parameter to pass back.

*Alternatives considered:* letting the studio own its own review and commit — rejected; two workflows committing to one repository is how a half-published pair happens, and it splits the failure path across two error workflows.

### D10. New workflows are created by an explicit, one-time create path

`scripts/apply_workflow_changes.py` can only edit existing workflows (`PUT /api/v1/workflows/{id}`) and activate them; it cannot create. Because every workflow in this change is new, the script gains an idempotent `--create` that `POST`s a whole workflow body once, keyed by name, and prints the new id; every later edit keeps using the existing field-level `PUT` path. This is the documented single exception to "never post a whole exported body", and it exists only for creation.

*Alternatives considered:* manual UI import — rejected as unreproducible and untestable; authoring exports without a create path — rejected because the next backup run overwrites them with the live state that lacks them.

### D11. The post identity is frozen at first draft

The slug is derived from the title once, at first draft, and frozen: a retry that changes the title updates the H1 only, never the slug or the asset filenames. `PUBLISHED_URL` and the committed paths bind to the frozen slug, so idempotency survives a title edit.

*Alternatives considered:* deriving the slug from the final title on every run — rejected; a late title edit would rename committed files and the URL.

### D12. Assets are referenced at draft markers

The article draft is instructed to emit one `<!-- asset:<type> -->` marker per requested asset type. The commit step replaces each marker with the asset's Markdown reference and alt text; a requested type whose marker is missing from the draft is appended at a default position rather than dropped. This keeps placement deterministic without asking the model to know file paths.

*Alternatives considered:* asking the article prompt for image paths directly — rejected; the paths are not known at draft time and model-authored paths drift.

### D13. Manual first, `#workflows` for review

The workflow ships with the schedule **inactive** and is exercised through the manual trigger until every path is verified; the schedule is activated afterwards. Reviews go to the existing `#workflows` channel (`C08RQNXQV3P`) that the LinkedIn lane already uses, so there is one place to watch and no new bot invitation.

*Alternatives considered:* start scheduled — rejected; a new workflow's first runs should be observed, not timed. A dedicated content channel — rejected for now; it adds configuration and a second place to watch for no benefit at this volume.

### D14. Single-flight, resumable review

Two scheduled ticks MUST NOT work the same article: the claim (`STATUS=QUEUE` → `IN_PROGRESS`) is written before any model call, and a run that finds an `IN_PROGRESS` row skips it. Review state is persisted per artifact, so a run that dies while waiting on Slack is resumed by the next tick from the stored state rather than restarted. A stale claim (an `IN_PROGRESS` row older than a threshold with no live execution) is recoverable by the error workflow or by hand.

*Alternatives considered:* hold one execution through all gates with no persisted state — rejected; `executionTimeout` is 3600s and a restart loses the loop. Allowing overlapping ticks — rejected; two writers to the same row and asset page. Skipping an asset's review on a text-only tweak — rejected; every pending review re-opens, so a fast path cannot immunize a stale artifact.

### D15. Pending work is a defined predicate, not an inference

The next action for an entry is read from an explicit predicate over `STATUS × ARTICLE_STATUS × asset states`, so a resumed run never has to guess whether it should draft, generate assets, re-present a review, or commit. Every transition writes the state that predicate reads:

| STATUS | ARTICLE_STATUS | assets | next action |
| --- | --- | --- | --- |
| `QUEUE` | — | none | draft the article |
| `IN_PROGRESS` (article) | not approved | none | resume/re-present the article review |
| `IN_PROGRESS` (assets) | `APPROVED` | any missing/unapproved | produce or re-present that asset |
| `IN_PROGRESS` (commit) | `APPROVED` | all `APPROVED` | commit |
| `PUBLISHED`/`CANCELLED`/`ERROR` | — | — | no work |

*Alternatives considered:* inferring from whichever field looks unfinished — rejected; it is exactly the ambiguity that makes resume non-deterministic once assets exist.

### D16. Cancelling an entry cancels its pending asset rows

Setting an entry to `CANCELLED` also marks that entry's non-terminal rows in this change's `article_assets` DataTable `CANCELLED`, in the same step, so no orphaned asset row can be re-presented or committed later.

*Alternatives considered:* leaving asset rows untouched — rejected; a cancelled article with a live asset row is one predicate bug away from publishing.

### D17. Verification is manual, and stated as such

There is no automated test for an n8n workflow in this repository. Verification is the manual trigger over every predicate row (D15) plus `--require-edge` graph checks on apply; this is the verification story, not an implicit gap.

*Alternatives considered:* implying CI coverage — rejected; the repo only tests the Sympozium delivery hook, and an unstated manual story reads as untested.

## Risks / Trade-offs

- **Direct-to-`main` publication of model-written content is public and irreversible in the moment.** → Two explicit, separate Slack approvals; the commit ref and URL are recorded in the row; rollback is `git revert` on `alvsanand`. Switching to a branch+PR later touches only D5's publish node.
- **The reused GitHub credential is broader than the bound.** → Measured 2026-10-16: it has `push` on `alvsanand/alvsanand`, and it is a classic PAT with `repo, write:packages` — so it reaches every repository that account can push to, which is more than this change's requirement allows. The workflow's own calls are bounded (each names `alvsanand/alvsanand`), so the loose half is the token; a fine-grained PAT scoped to that repository's contents would close it. Left open deliberately rather than silently accepted, because a token that can write anywhere is the kind of thing that stops being noticed.
- **The draft now lives in an n8n DataTable.** → A DataTable is instance-managed state, backed up with the instance database; a missing row is an error, never an empty article.
- **Human review is slow and a run can die while waiting.** → Per-artifact state is persisted and the D14 single-flight/resume rule resumes the next tick from that state; a stale claim is recoverable by the error workflow or by hand. `executionTimeout` no longer defines the review window.
- **Fetched source content is untrusted and can carry prompt injection.** → The article prompt treats fetched content as reference material, not instructions, and the only write target is the blog commit; per repo policy, deterministic choices live in code and the model only writes prose.
- **An article retry can leave an approved asset stale.** → The article is approved before its assets are generated and a review message names each artifact's round; a re-render is not spec-pinned, because the studio edits the composition its session holds rather than authoring a copy of it. If mismatch recurs, revisit whether an article change invalidates asset approvals.
- **A raster hero is carried inline, so the entry point records it.** → The `image` type answers with its data URL, and no store can fetch bytes made inside n8n, so the entry point's `execution_data` grows by the hero's size (measured ~2.3 MB for one 1080x1350 png on the LinkedIn lane). `saveDataSuccessExecution` stays at its default here; if that record grows, the fix is the studio's raster branch, not a second upload path.
- **The committed export can drift from the live instance.** → Apply with `scripts/apply_workflow_changes.py`, pairing changes with `--require-edge`, and re-read after the PUT to confirm fields landed; the export is a backup, not the source (repo rule).
- **The create path is a new capability on the apply script.** → Scope `--create` to creation only, idempotent by name, print the new id, and prove it with a throwaway workflow created then edited through the existing `PUT` path; a same-named workflow must be left untouched.
- **A requested asset marker can be missing from the draft, or a title edit can move the URL.** → The marker contract defaults a missing type to a fixed position rather than dropping it (D12), and the slug is frozen at first draft so a title edit cannot rename committed files (D11).
- **An unwired failure is invisible.** → `settings.errorWorkflow` on the entry point, sub-workflows raise, and the error workflow clears the row; state this in the change and verify before enabling the schedule.

## Migration Plan

1. Add the `article_queue` page and its columns to `content_planner` (no `IMAGE_*`), create the `article_drafts` and `article_assets` DataTables by hand in the UI, and author one test row.
2. Add the prompt files under `agents/n8n/prompts/` (they reach the runtime through the existing `DownloadTemplate` GitHub read).
3. Extend `scripts/apply_workflow_changes.py` with the idempotent `--create` (D10), verify it with a throwaway workflow, then create the `Article Creator` sub-workflow and the error workflow live; capture the error workflow's new id before wiring it.
4. Author the entry-point `Article Content Writer` workflow with the schedule **inactive** (D13), create it, and exercise every path with the manual trigger: approve/approve, approve/reject-one-asset/retry, reject-article/retry, cancel, and a forced LLM error. Confirm the single-commit publish and the row states.
5. Wire `settings.errorWorkflow` to `Article Content Writer Error`, verify it clears and notifies, then activate the schedule.
6. Rollback: deactivate the workflow (schedule stops), set the live row back to `QUEUE`; revert the `alvsanand` commit if one was published in error. No cluster state is involved.

## Gate findings (authoring)
 
Two reference-shape facts, read off the installed nodes rather than guessed, and both came out of a blocker: the entry point's sheet page and the two Data Tables do not exist yet, so an export that could only name them by numeric id could not be authored at all.

- **A Google Sheet can be addressed by name.** `Google/Sheet/v2`'s `sheetName` resource locator supports `{__rl: true, mode: "name", value: "<title>"}`, and the node's own builder hint says a title placed in `list` or `id` mode cannot resolve. The LinkedIn exports use `mode: "list"` with the gid because they were built against a live page. Neither name nor gid is stable-forever, but the name is the one the change itself specifies for the page, so the exports use it until the page exists and a gid can be read.
- **A Data Table can be addressed by name too.** `DataTable`'s `dataTableId` locator declares modes `list` and `name` (`common/fields.js`). So `article_drafts` and `article_assets` can be wired before either table is created.

- **The `DataTable` node carries its own table management.** Its row operations include
  `upsert` (keyed by filter conditions), and its table operations include `create`. So a round of
  review upserts its row instead of accumulating one per attempt, and the two tables in section
  1 can be created by running a node.
- **The public API has DataTable endpoints, so the tables are scriptable after all.** The earlier
  [UNVERIFIED] resolved the other way: `GET /api/v1/data-tables` lists them with their columns,
  `POST /api/v1/data-tables` answers 201 and `DELETE /api/v1/data-tables/{id}` answers 204 —
  measured 2026-10-16 with a throwaway table that left no residue. `/api/v1/datatables` and
  `/api/v1/dataTable` are 404, so the hyphenated path is the one, and `/api/v1/projects` is 403
  on this license (`feat:projectRole:admin`), which is why the table's own `projectId` has to be
  read from a table rather than listed.
- **A Data Table filter condition is `eq` / `neq` / `lt` / `isNotEmpty`**, not `notEqual`. Read
  off `DataTable/common/methods.js` after an invalid condition was written into a filter here;
  the values are load options, so nothing validates them offline and an invalid one would fail
  at run time on that node only. `test_article_entry_point.py` keeps every filter condition in
  the entry point honest by asserting the nodes that matter, not by enumerating the vocabulary.

Consequence: the human steps in section 1 are no longer a precondition for authoring anything,
only for running it.

## Entry point: node plan

**Implemented** as `agents/n8n/workflows/article_content_writer.workflow.json` (73 nodes, a create
body; live creation is 6.1). The graph follows this plan with four deliberate departures, each
because the plan's shape would have failed at run time:

- the queue is read in two steps, not one: `pick_candidate` chooses the entry from the sheet
  alone and `read_asset_rows_for_entry` then reads **that entry's** asset rows, so the asset read
  is bounded by the entry instead of a table that grows. `select_article_to_queue` turns the two
  into `PHASE` and `PENDING_ASSETS`;
- a raster asset's bytes are stored on its `article_assets` row (`DATA_BASE64`) at render time.
  The plan left them local, but a raster has no durable handle at all - the studio makes those
  bytes inside n8n and keeps no copy - so a commit resumed after a died run would have had
  nothing to commit. An agent-authored asset is re-fetched from its `S3_KEY` instead, so no
  video-sized payload ever reaches the row;
- the non-fast-forward retry is a real second attempt: `patch_ref`'s error output re-reads
  `heads/main` and rebuilds tree and commit on the branch's new head, because replaying the same
  `PATCH` cannot succeed;
- the draft row is written with `upsert` keyed on `ENTRY_ID`, so a round updates the row instead
  of adding one per attempt.

Original plan, for reference. Every shape it needs already exists in `linked_in_post_sharing`
(read, claim, `sendAndWait` double approval, the Retry/Cancel form, cancel branches, the
publish-time row update) or in `visual_studio_test` (the DataTable write and the download
URL), so the build is a clone-and-rewire rather than new node types.

Order and wiring:

1. `click_trigger` (manual) and `schedule_trigger` (schedule) → `read_article_queue`
   (Google Sheets, `documentId` unchanged, `sheetName` by name `article_queue`).
2. `select_article_to_queue` (Code) — the D15 predicate, lowest `row_number` first, and a row
   already `IN_PROGRESS` with a live execution is skipped (D14).
3. `update_status_in_progress` (Sheets update by `row_number`) — writes `STATUS` and
   `EXECUTION_ID = $execution.id` **before** any model call, which is what makes the claim
   single-flight and lets the error workflow find the row.
4. `if_has_link` (If) → `download_content` (HTTP GET, `onError: continueRegularOutput`) and
   both its outputs → `set_link_flags` (Code) — one item always, carrying `LINK_USED` and the
   fetched text, so an unreachable link continues from topic and description and records that
   the link was not used. The flag is set by this node, never read from `$json.error`, because
   a non-AI node forwards its input unchanged on failure.
5. `execute_article_creator` (Execute Workflow → `nPBkIpeObC1Om0LH`) with `MAX_WORDS`
   `toNumber() || 1200`, `ASSET_TYPES` from the row, `SESSION_ID` `blog-<ENTRY_ID>` and
   `FEEDBACK` from the retry form when it ran.
6. `check_subworkflow_error` (Switch on `ERROR` empty) → error branch to
   `stop_and_error`; success branch continues.
7. `store_draft` (DataTable append, table by name `article_drafts`) →
   `convert_to_file` (`convertToFile`) → `upload_draft_file` (Slack file) →
   `update_article_drafted` (Sheets: `ARTICLE_TITLE`, `ARTICLE_REF`, `ARTICLE_ROUND`,
   `ARTICLE_STATUS=DRAFT`, `STATUS=WAITING_APPROVAL`).
8. `notify_article_review` (Slack `sendAndWait`, `approvalType: double`, message naming the
   entry, the round and the uploaded file) → `switch_user_accept` → approved:
   `execute_visual_studio`; rejected: `notification_retry_or_cancel` (`sendAndWait`
   `customForm`, Retry/Cancel + Feedback) → `switch_user_retry` → Retry returns to step 5
   with the feedback, Cancel → `update_status_cancelled` + `set_error_cancelled`.
9. `execute_visual_studio` (Execute Workflow → `2pSrRNmYR2jkX1JG`) with
   `CONTENT` = the draft body, `ASSET_TYPES` = the row's list (the `image` hero always in it),
   `SESSION_ID` = `blog-<ENTRY_ID>`, `FEEDBACK` = the asset's own feedback when one is being
   retried. `FORCE`/`STYLE`/`SCENES` stay blank.
10. `split_assets` (Code) — one item per `ASSETS[]` entry, carrying `ASSET_TYPE`, `STATUS`,
    `ERROR`, `CONTENT_TYPE`, `S3_KEY` and `FORMAT`; an entry whose `STATUS` is not `RENDERED`
    keeps its reason and takes no review.
11. `store_assets` (DataTable append, table by name `article_assets`, keyed `ENTRY_ID` +
    `ASSET_TYPE`) → per asset, `fetch_asset_bytes`: the raster `image` type reads its inline
    data URL, an agent type asks the utils server for a signed URL (`temp_retrieve`) and
    downloads it — the shape `linked_in_post_sharing`'s video branch already uses. Both
    converge on `upload_asset_file` (Slack file) → `notify_asset_review` (`sendAndWait`
    double) → `switch_asset_accept` → rejected: the asset's own feedback →
    `notification_retry_or_cancel_asset` (`sendAndWait` `customForm`) → Retry re-enters step 9
    for that one type, Cancel retires that asset only.
12. `all_assets_approved` (If over the asset rows) → publish:
    `get_posts_dir` (GitHub `GET /repos/alvsanand/alvsanand/contents/docs/blog/posts`) →
    `derive_slug` (Code, frozen on the first draft: reuse `ARTICLE_REF`'s stored slug when one
    exists) → `build_commit_files` (Code: front matter, the asset references replacing their
    `<!-- asset:<id> -->` markers with a default position for any marker the draft omitted,
    one item per file) → `create_blobs` (HTTP, one POST per item) → `create_tree` →
    `create_commit` → `patch_ref` → `record_published` (Sheets: `PUBLISHED_URL`, `COMMIT_REF`,
    `PUBLISHED_AT`, `STATUS=PUBLISHED`, each asset row's committed path) →
    `send_published_notification` (Slack).
13. `Article Content Writer` sets `settings.errorWorkflow` to `Article Content Writer Error`;
    the sub-workflows set none. The schedule stays inactive until 6.2–6.5 pass (6.6).

Traps to carry into the build, all already paid for elsewhere in the repository:

- The draft reaches Slack as an uploaded file: `sendAndWait` text truncates around 3000
  characters and a 1200-word draft is several times that.
- `binaryMode` cannot be set through the API, so it stays out of the create body.
- Each DataTable and Sheet reference uses `mode: "name"` until the page and the tables exist,
  then the gid/table id can be read back and swapped in one edit.
- `saveDataErrorExecution` stays at its default; the raster hero's data URL (measured
  943,620 bytes for one 928x1152 png) is the only asset byte this workflow ever carries.

## Live measurements (2026-10-15)

`Article Creator` created live and exercised through a temporary webhook probe that was deleted
afterwards, so these are readings and not inferences.

- **`DownloadTemplate` reads the prompts from `main`.** The first probe answered 404 at its
  `download_template` node because `prompts/article_writer.md` existed only locally: the file
  is fetched by the `github` node from the backup repository, so a prompt is inert until it is
  pushed. That is the documented "prompt files are live on push" property, and it is also why
  the categories file behind the `CATEGORIES` check needs the same push.
- **The model obeys the budget.** `MAX_WORDS=5` produced a 5-word draft and no rejection, so
  the over-budget branch is not reachable by shrinking the budget; forcing it needs the draft
  to be pushed past the bound (an `EXTRA_PROMPT` asking for 250 words against `MAX_WORDS=50`
  gave `OVER_BUDGET: 331 words against MAX_WORDS=50`).
- **The count is the reviewer's count.** `WORD_COUNT` matched an independent count over the
  same text with the markers stripped, in both the 216-word and the 331-word draft, so the
  number in the rejection is not a second estimate.
- **The marker contract is load-bearing, not tidy.** One of three live `image,svg` drafts came
  back with `<!-- asset:image -->` only. A requested type whose marker the model omits must
  still be placed and committed (D12), which is the half task 4.9 exists for.
- **`MAX_WORDS` missing fails loudly.** An omitted `MAX_WORDS` ended the sub-execution `error`
  at `parse_article` rather than drafting against a guessed bound; the caller's
  `executeWorkflow` node failed with it, which is the propagation D7 relies on.
