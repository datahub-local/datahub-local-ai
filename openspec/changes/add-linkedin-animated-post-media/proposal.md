# Proposal

## Why

The LinkedIn pipeline can attach exactly one thing to a post: a still image generated by the image model. The Visual Studio workflow (archived 2026-10-01, `openspec/specs/visual-studio/spec.md`) now renders a deterministic animated infographic from a content spec and assembles it as an animated file, which is the one thing a still cannot do — a moving diagram of the same idea the post is about. The moved infographic is worth more in-feed than another static hero.

## What Changes

- Add an **opt-in per-row media choice** to the LinkedIn pipeline: a `content_queue` row carrying `POST_MEDIA=ANIMATED` publishes its post with a Visual Studio animated infographic; a blank or `STATIC` value keeps today's image path byte-for-byte unchanged, so the default behaviour of every existing row does not move.
- Add an **animation branch**: call `Visual Studio` as a sub-workflow with `ASSET_TYPES=diagram_animated_linkedin` and the post text as `CONTENT`, then take a Slack approval for the animation through the same Retry/Cancel + Feedback form the image uses; a rejection re-authors the animation with that feedback and re-presents it. There is no frozen-spec step: a post has one media asset, so there is no second variant to keep in step.
- Add a **fallback**: when the animation is reported unavailable or fails to render, the run continues into the existing `LinkedIn Image Creator` path, so a post is never blocked on the animation.
- Attach the approved animation to the LinkedIn node as its media, with the content type the studio returned, instead of the still image.
- **Make a type's declared format authoritative (studio change).** The assembler currently tries `img2webp` first and reaches GraphicsMagick only when that fails, so a type declaring `format: gif` would still produce WebP. The declared format becomes the encoder selector: `gif` assembles with GraphicsMagick, `webp` keeps today's img2webp-then-GM order. This is a requirement change on the `visual-studio` capability, not a caller-visible change for existing types.
- Add the registry type **`diagram_animated_linkedin`** — same template and authoring as `diagram_animated`, but `format: gif` and a budget of **8 fps / 24 frames / 1080 px** (3 s, ≈35M pixels total) so the animation stays inside LinkedIn's documented GIF limit of 500 frames or 36,152,320 pixels (design D2).
- Add one `content_queue` column, `POST_MEDIA`. Nothing else about the sheet changes.

## Capabilities

### New Capabilities

- `linkedin-post-publishing`: the scheduled pipeline that turns a queued source into a published LinkedIn post — here, specifically which media a post may carry, how that media is approved, and what happens when it cannot be produced. A sibling change in flight (`fix-linkedin-post-review-gate`) also adds to this capability from the same missing main spec; both deltas are ADDED and merge in either archive order.

### Modified Capabilities

- `visual-studio`: the animation requirement gains the rule that a type's declared format selects the encoder, so a `gif` type is assembled as GIF rather than falling back to it.

## Impact

- **`agents/n8n/workflows/linked_in_post_sharing.workflow.json`**: the animation branch (studio call, approval gate, binary conversion, media attach) and the `POST_MEDIA` switch. Applied live with `scripts/apply_workflow_changes.py`, never assumed from the export; `fix-linkedin-post-review-gate` edits this same workflow and must land first (design D6).
- **`agents/n8n/workflows/visual_studio.workflow.json`**: `build_assemble` selects the encoder from the type's declared format.
- **`agents/n8n/datasets/visual_types.json`**: the new `diagram_animated_linkedin` type. Fetched through `DownloadTemplate` from GitHub `main`, so it must be pushed before a live run resolves it.
- **`content_planner` / `content_queue`**: one new column, `POST_MEDIA`.
- **LinkedIn**: a GIF attachment on a real post. Whether LinkedIn animates it in-feed, and how it treats the 4:5 aspect at 1080 px, are `[UNVERIFIED]` and are the first gate (design "Gate findings"); nothing in this repo can answer them.
- **No change** to `datahub-local-core`, `datahub-local-ai-mcp`, Sympozium, the blog pipeline (`add-content-writer-agent`) or the studio's response contract.
